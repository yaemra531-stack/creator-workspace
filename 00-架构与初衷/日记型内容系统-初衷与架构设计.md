# 日记型内容系统 —— 初衷与架构设计 v1

## 为什么要做这个系统

### 背景

内容创作原计划是"干货型"先行，走完整的16步工作台流程。但实际执行25小时后，日记型投入为0，第14天仍未发布任何正式作品。问题不在执行力，而在顺序：干货型天然要求"反复做过、验证过才敢出"，这个前提在冷启动阶段根本不成立。

因此决定：日记型插队先跑，干货型继续在后台按16步走，两条线并行，不互相替代。

### 为什么日记型值得先做

1. **练小红书表达语言**——小红书的文字节奏、标题习惯只能靠高频、低门槛的输出练出来，干货型练不出这种手感。
2. **练拍照展示能力**——日记型的照片不需要参考图匹配，是最直接的实拍练习场，练熟后能直接用到干货型配图上。
3. **市场调研**——日记型发得快、发得多，等于用低成本反复测试"读者对什么话题真正有反应"，等做干货型时不再是凭空猜测，而是有真实反馈支撑选题。

参照案例：卡兹克重启公众号后先经历"起号期"，靠大量低门槛输出练手感、摸清读者反应，再转向深度内容，验证过同一顺序有效。

### 为什么还要搭建一个记录系统（不只是执行流程）

日记型本身要保持"轻"——不能变成第二个16步工作台。但对话和执行经验会随着时间和对话轮次增多而碎片化丢失：今天想清楚的四个结论，如果没有落地成文档，下次讨论要重新梳理一遍。

搭建系统的目的不是让"写日记"这件事变复杂，而是让**方法论、决策、迭代经验**能够沉淀、不丢失，让未来的AI Agent每次介入时能直接读取当前状态往下走，而不需要用户重新口述背景。

对应之前做项目的经验：有GitHub + README + 功能推送记录，之后想改进项目直接把仓库交给Agent即可，不必担心信息随对话消失。

**结论：系统要搭，但搭的是"记录系统"，不是"生产流程"。** 两者并行推进，互不等待。

## 系统架构：前中后三阶段

系统按照内容产生到发布的自然流程，分为三个阶段。每个阶段解决一个具体问题，用最轻量的方式落地。

### 前阶段：按板块随时记录（素材池）

**解决的问题**：每天学习/工作分成几个板块（如雅思口语、雅思写作、AI工作台搭建等），每个板块过程中都会产生真实的感悟、卡点、小发现——这些转瞬即逝，不记录就会消失。

**做法**：

- 按当天涉及的板块分类记录，而不是笼统地"随便记"
- 冒出一句真实的话、一个卡点、一个发现，当场记下一句即可，不用完整、不用有逻辑
- 关键约束：记录动作本身不能打断正在做的正事，成本必须极低（一句话、几秒钟）

**产出**：一个按板块分类的素材本（原始碎片记录）。

### 中阶段：固定时间整理成日记（成型）

**解决的问题**：素材记了很多，但不会自动变成能发布的内容，需要一个固定的处理动作。

**做法**：

- 固定一个时间点（例如每天下午），回看前一天/前一段时间记的素材
- 从素材里筛选出真实、有点意思的条目——不是所有素材都要转化，效果不好的可以舍弃
- 用懂懂日记式的"拉家常"语气扩展成3-5句话，像跟朋友随口说，而不是写文章
- 话题调性对齐薏米（AI赛博工头）的简单风格：一张现成照片配文字，或一段10秒小视频

**产出**：一篇可以直接发布的日记型内容。

### 后阶段：发布（暂不深入设计）

**当前判断**：发布之后的环节（比如互动、反馈追踪、二次利用）目前难以控制，也不是现阶段的重点。优先把前两个阶段做扎实——能稳定产出素材、能稳定转化成内容——已经是当前值得达到的目标。后阶段留白，等前两阶段跑顺之后再补充设计，不提前过度设计。

## 给Agent的执行说明

这份文档是当前系统设计的**第一版初衷与架构**，交给Agent执行时请注意：

- 前阶段和中阶段是当前需要落地的核心，后阶段暂不展开
- 系统的作用是记录和沉淀方法论，不是把"写日记"这件事变复杂
- 每次日记型流程有实际调整（比如发现某个环节该改），都应该更新这份文档，作为版本迭代记录
- 这份文档可以作为项目README的基础内容
